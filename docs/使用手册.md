# LexBridge 法桥 · 使用手册

面向**拿到这个仓库的人**。目标只有一个：让你在十分钟内把系统跑起来，
知道每一个页面里什么是真的、什么是还没做的，而不用去读源码猜。

> **先读这一段，能省掉后面的困惑。**
> 这是一个分阶段交付的作品集项目。**知识库这条链路是完整可用的**——
> 2,562 条真实法条、可筛选、可展开原文、可溯源到公开来源；
> 认证、多租户隔离、审计留痕也都是真的。
> 而**「法律咨询」与「知识入库」的服务端尚未实现**，那两个页面会显示一段
> 明确的说明而不是一个能用的界面。这不是故障，是现状。
> 权威口径永远是 README 的「已知边界」表，本手册只是把它展开成可操作的步骤。

## 1. 你需要什么

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| Docker | 20.10+ | 唯一必需的依赖 |
| Docker Compose | v2 | `docker compose`（带空格），不是 `docker-compose` |
| 空闲端口 | `8088`（可改） | 只暴露一个端口；数据库与缓存只绑 `127.0.0.1` |

以下依赖**只在你要改代码时才需要**，纯粹想跑起来看看的话不必安装：

| 依赖 | 版本 | 用于 |
| --- | --- | --- |
| JDK | **21**（不是 17） | `backend/`，版本不对会以 "release version 21 not supported" 失败 |
| Node.js | 22+ | `frontend/` |
| Python + uv | 3.11 | `ai-service/` |

> **不需要任何 API Key。** 语料与预计算向量都随仓库提交，首次启动自动灌库。
> 只有要用真实模型跑咨询链路时才需要 `SILICONFLOW_API_KEY`——而那条链路目前
> 服务端还没实现，所以现在也不需要。

## 2. 启动

```bash
cp deploy/.env.example deploy/.env
```

生成两个密钥填进 `deploy/.env`（其余可以留默认值）：

```bash
openssl rand -base64 48     # 填给 JWT_SECRET
openssl rand -base64 48     # 填给 INTERNAL_TOKEN_SECRET
```

然后：

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml up -d
```

首次启动大约 **2 分钟**（含镜像构建），之后每次 30 秒左右。启动顺序是编排好的：

```
postgres → api（跑数据库迁移）→ seed（灌入 2,562 条法条 + 319 条向量）→ web
```

**`web` 在灌库完成前不会启动**，因此你不会打开页面看到一个空的知识库。

### 打开哪个地址

```bash
grep WEB_PORT deploy/.env
```

默认是 `80`，本机示例配置里是 `8088`。**以你 `deploy/.env` 里的值为准**，
不要照抄文档里的端口——照抄会打开一个没有服务的地址。

### 六个容器，其中一个是干完就退出的

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml ps
```

| 容器 | 作用 | 期望状态 |
| --- | --- | --- |
| `postgres` | PostgreSQL 16 + pgvector | Up (healthy) |
| `redis` | 缓存与会话工作态 | Up (healthy) |
| `api` | Spring Boot 业务主干 | Up (healthy) |
| `ai` | Python AI 运行时（不对外暴露端口） | Up (healthy) |
| `seed` | **一次性**灌库任务 | **Exited (0)** ← 这是正常的 |
| `web` | nginx + 前端产物，唯一对外端口 | Up (healthy) |

`seed` 显示 `Exited (0)` 是**成功**的意思。若是 `Exited (1)`，看
`docker compose logs seed`——原因会写在里面，最下面一节列了常见几种。

## 3. 怎么进去（不需要注册）

**本系统没有自助注册，这是产品口径而不是待补的功能。** 多租户企业工具的账号
由管理员开设——PRD 里「管理本租户成员」是租户管理员的权限。但对刚拿到仓库的人，
这意味着会停在一个填不出"租户标识"的登录页上。

所以登录页顶部有**三个「一键进入演示」的按钮**，点一下就进去了：

![登录页](images/01-login.png)

三个按钮分别对应三个角色，各自标注了登录后能看到什么。**点击走的是真实的登录流程**
（JWT 签发、租户解析、审计留痕一个都不少），它省掉的只是"先去文档里翻租户标识"这一步。

按钮下面的「或手动填写」是同一个表单，走同一条路径——想验证真实登录流程的话，
用下面的凭据填一遍即可。

> 演示模式关闭时（`deploy/.env` 里 `DEMO_DATA=false`）这一块**整个不渲染**，
> 生产部署上不会出现任何入口。这不是前端隐藏，是服务端返回 `enabled=false` 时
> 页面根本不渲染那一块——接口本身也不返回任何账号。

### 三个账号

口令统一是 `LexBridge@2026`。

| 租户标识 | 用户名 | 角色 | 登录后能看到 |
| --- | --- | --- | --- |
| `demo-law` | `admin` | 系统管理员 | 知识库、入库复核、法律咨询、审计日志 |
| `demo-law` | `lawyer` | 执业律师 | 法律咨询、会话历史 |
| `demo-law` | `compliance` | 合规官 | 审计日志 |
| `acme-law` | 同上三个 | 同上 | 同上，但**看不到 demo-law 的任何数据** |

登录页要填**三项**：租户标识、用户名、口令。租户标识不是邮箱后缀，
它是 `demo-law` / `acme-law` 这样的短代码。

**登录后各自落在哪一页**（按角色菜单里的第一项，不是写死某一页）：

| 角色 | 落地页 |
| --- | --- |
| 系统管理员 | 知识库 —— 他的主工作面，里面有 2,562 条真实法条 |
| 执业律师 | 法律咨询（该页服务端尚未实现，会显示说明） |
| 合规官 | 审计日志 |

> **为什么要两个租户。** 这是本项目最值得看的一处设计：多租户隔离。
> 用两个浏览器（或一个正常窗口 + 一个隐私窗口）分别登录 `demo-law` 和 `acme-law`，
> 在审计日志里看到的将是**各自独立的记录**。
> 这不是前端过滤出来的效果——令牌里带着租户身份，数据库层还有行级安全策略兜底。

## 4. 分角色走一遍

### 4.1 系统管理员（`demo-law` / `admin`）——能玩的东西都在这里

登录后侧栏有四项。逐项说明：

**知识库** ← 这一页是真的，也是本项目的核心展示

- 列表里是 **8 部法规、2,562 条法条**，覆盖爱尔兰与荷兰两个法域
- 每行的「法域 / 版本 / 生效区间 / 状态 / 法条数」都来自真实语料
- 爱尔兰的法规会显示 **`（年份精度）`**：爱尔兰官方站点不提供机器可读的通过日期，
  系统如实标注"只能确定到年"，而不是编一个具体日期
- 顶部两个下拉可以按**法域**和**发布状态**筛选
- **点任意一行**会打开右侧详情面板，里面有法规原文出处（`source_url`）

**审计日志** ← 也是真的

- 记录由后端自动写入，界面**没有**任何新增/修改/删除入口——一个能被调用方
  改写的审计日志不具备证据价值
- 你刚才的每一次登录、每一次审计查询都在里面
- 点任意一条的 **traceId** 可以按它反查："这一串到底发生了什么"
- 顶部可按时间、操作人、结果（含"只看红线拒答"）筛选

**法律咨询** / **入库复核** ← 这两页的服务端尚未实现

点进去会看到一段说明，逐条列出缺什么。界面不会报错，也不会假装能用。

**关于页面右上角的「发布当前版本 / 回滚」与「上传法规」**：这些按钮背后的接口
同样未实现，点下去会提示"服务端尚未实现（接口返回 404）"。知识库列表本身不受影响。

### 4.2 执业律师（`demo-law` / `lawyer`）

侧栏只有两项：**法律咨询** 与 **会话历史**——而这两项都依赖尚未实现的咨询链路。

坦白说，律师这个角色在当前阶段**没有可操作的功能**。写在这里而不是含糊过去，
是因为"哪个角色现在能看到什么"本身就是这套权限设计的一部分。

### 4.3 合规官（`demo-law` / `compliance`）

侧栏只有**审计日志**一项，落地页就是它。这个角色刻意只有只读入口：
他的职责是审阅与留痕，不是操作。

他不该有的东西也**真的没有**——不只是菜单里不显示。这是实测过的：

| 请求 | admin | lawyer | compliance |
| --- | --- | --- | --- |
| `GET /api/audit-logs` | 200 | **403** | 200 |
| `GET /api/statutes` | 200 | 200 | 200 |

> 律师那一栏的 403 值得单独说一句。**在修复之前，这里三个角色全是 200**——
> 角色差异只做在了前端菜单上，而前端隐藏入口拦不住任何人：
> 拿律师的令牌直接请求审计接口就能拿到全部记录。
> 项目自己的设计声明是「前端的所有权限判断都只是体验优化，真正的强制在后端」，
> 现在这句话才成立。依据是 PRD §3.8 的权限矩阵。

## 5. 验证这套东西是真的

不想只看界面的话，有一条命令可以把上面所有结论跑一遍：

```bash
python scripts/verify_demo.py
```

它用**标准库**直接打接口，检查 20 项：三个账号能否登录且角色正确、
语料是否真的灌进去了、每条法规是否都带来源 URL、审计里有没有登录留痕、
关键词反查是否真的生效、**两个租户的数据是否互不可见**、
**律师是否真的被服务端挡住（403）**、未实现的接口是否如实回 404 而不是 500。

当前是 `20/20 passed`。输出全用 ASCII，因为 Windows 控制台默认 GBK，
中文和 emoji 会让脚本在打印阶段就崩掉——而那看起来像"验收失败"。

## 6. 常见问题

**Q：打开页面是空白 / 连接被拒绝。**
端口不对。`grep WEB_PORT deploy/.env` 看真实值，别用文档里的示例端口。

**Q：`docker compose up` 卡在 `seed` 上。**
先看 `docker compose logs seed`。三种常见原因：
① 语料文件缺失（`deploy/seed/corpus/*.jsonl` 应当有两个文件）；
② 向量文件缺失——这**不算失败**，日志里会是 WARNING，法条仍会灌入，
只是语义检索没有覆盖；③ 数据库没起来，看 `docker compose logs postgres`。

**Q：登录提示"用户名或密码错误"。**
检查租户标识是否写成了邮箱——它应当是 `demo-law` 或 `acme-law`。
若两者都对，确认 `deploy/.env` 里 `DEMO_DATA=true`（默认就是），
然后 `docker compose logs api | grep 演示账号`，应当能看到创建了 6 个账号
（两个租户各三个）。

**Q：我把 `deploy/.env` 里的 `POSTGRES_PASSWORD` / `DB_PASSWORD` 改了，然后就起不来了。**
数据库口令只在**首次初始化数据卷时**生效。改了 `.env` 而沿用旧数据卷，
`api` 会以 `password authentication failed for user "lexbridge"` 启动失败。
要么改回原口令，要么清掉数据卷重来：

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml down -v
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml up -d
```

**Q：`mvnw` 报 "release version 21 not supported"。**
`JAVA_HOME` 指向了 JDK 17。不必改系统配置，可以在命令里临时覆盖：

```powershell
$env:JAVA_HOME="C:\Program Files\Microsoft\jdk-21.0.12.101-hotspot"
.\mvnw.cmd -B verify
```

**Q：前端页面显示"加载失败"而不是"服务端未实现"。**
两者的区别是有意的：**404 表示这个接口不存在**（尚未实现），
其他错误才是真的出问题了。若未实现的页面显示"加载失败"，
说明请求返回的不是 404——把那条的 traceId 拿出来查审计日志。

**Q：想重新灌一次库。**
`docker compose ... down -v` 删掉数据卷再 `up -d`。
`seed` 是幂等的：已存在的法规版本会整组跳过，向量走 upsert，
重复执行不会产生重复数据。

**Q：怎么把语料换成别的法规。**
替换 `deploy/seed/corpus/*.jsonl`（格式见 `deploy/seed/corpus/SOURCES.md`）。
向量文件需要重新生成——见 `deploy/seed/vectors/README.md`，
并且在换语料之后跑一次 `cd ai-service && uv run pytest tests/test_seed_vectors.py`，
其中一条测试专门守"语料与向量是否同步"。

## 7. 现在**不**能用的部分（诚实清单）

写清楚比含糊过去有用。以下是当前阶段的真实边界。

| 功能 | 状态 | 点下去会看到什么 |
| --- | --- | --- |
| 登录 / 登出 / 会话恢复 | ✅ 可用 | 正常 |
| 知识库列表与筛选 | ✅ 可用 | 8 部法规，2,562 条法条 |
| 法规详情 | ✅ 可用 | 原文出处、生效区间、日期精度 |
| 审计日志查询与 traceId 反查 | ✅ 可用 | 真实留痕 |
| 多租户隔离 | ✅ 可用 | 两个租户互不可见 |
| 角色权限 | ✅ 可用 | 律师读审计被服务端挡（403） |
| **法律咨询**（两类） | ❌ 服务端未实现 | 一段说明，列明缺哪三个 ai 端点、哪五个 backend 端点 |
| **会话历史** | ❌ 服务端未实现 | 同上，依赖咨询链路 |
| **知识入库**（上传 / 复核 / 发布 / 回滚） | ❌ 服务端未实现 | 上传与发布按钮会提示接口未实现 |
| 扫描件 PDF 的 OCR | ❌ 不支持 | LlamaIndex core 不含 OCR |
| 多语言界面 | ❌ 仅中文 | 语料支持多语言，界面未做 i18n |

语料侧另有两处未达标，已在 README 的「已知边界」里逐条记录：
覆盖 2 个法域而非 6 个（2,562 条 vs 目标 5,000 条），
以及爱尔兰的生效日期只精确到年。**这两条是如实标注，不是估算。**
